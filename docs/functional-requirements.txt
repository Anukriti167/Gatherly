Document overview
This document contains the consolidated functional requirements for Gatherly. Requirement identifiers (FR-001 to FR-230) are retained to support discussion, implementation tracking, testing and future revisions.
The requirements are organised by product capability. The final section records the additional requirements introduced for the initial publication approval workflow.

2.12 Event change proposals and unanimous approval
ID
 | Functional requirement
 | FR-132
 | Allow an owner or co-admin to create a change proposal for a published event.
 | FR-133
 | Support proposals affecting parent event details or individual activities.
 | FR-134
 | Support proposals for schedule changes, venue changes, participation changes, activity changes and event cancellation.
 | FR-135
 | Include description, proposed changes, proposer and creation timestamp in each proposal.
 | FR-136
 | Maintain a version number for each change proposal.
 | FR-137
 | Identify and record required approvers when a proposal is created.
 | FR-138
 | Allow each required approver to approve or raise an objection to a proposal.
 | FR-139
 | Do not automatically reject a proposal when one or more approvers disagree; unanimous approval is required for applicable operational changes to a Published event.
 | FR-140

 | FR-141
 | Allow co-admins to discuss and suggest modifications to pending proposals.
 | FR-142
 | Allow the proposer to revise a proposal.
 | FR-143
 | Create a new proposal version on revision and invalidate approvals for the previous version.
 | FR-144
 | Publish proposed changes only after all required approvers approve the same proposal version.
 | FR-145
 | Apply approved changes to the relevant event or activity.
 | FR-146
 | Preserve the original required approver set for pending proposals.
 | FR-147
 | Allow a proposer to withdraw a proposal.
 | FR-148
 | Record withdrawn proposals separately from rejected proposals.
 | FR-149
 | Maintain approval, objection, revision and discussion history.
 | FR-150
 | Notify relevant co-admins when proposals are created, revised or approved.
 | FR-151

 | FR-152

2.21 New requirements — initial publication approval
ID
 | Functional requirement
 | FR-222
 | Require unanimous approval from the event owner and every co-admin before an event can be initially published.
 | FR-223
 | Move an event into Pending Approval when an authorised administrator initiates publication.
 | FR-224
 | Record the required approvers as a fixed snapshot when a publication approval round is initiated.
 | FR-225
 | Allow each required approver to approve the specific event version submitted for publication.
 | FR-226
 | Keep the event unpublished and prevent guest invitations from being sent until all required approvers approve the same version.
 | FR-227
 | Allow an approver to request changes, returning the event to Draft for revision.
 | FR-228
 | Invalidate all approvals and start a new approval round if the event is edited while Pending Approval.
 | FR-229
 | Record publication approval decisions, approver identity, timestamps, event version and comments.
 | FR-230
 | Notify required approvers when publication approval is requested and notify relevant administrators when the event is published.
